## 修正1: 例示 regex の差し替え(「ルールファイル仕様」節)

rev.2 の `no-force-push` 例示 regex には語順依存の穴がある。

| | regex | `git push origin main --force` |
|---|---|---|
| 旧(rev.2) | `git\s+push\s+\S*\s*(--force\|-f)\b` | **すり抜け**(`\S*` は1トークンしか飛ばせない) |
| 新(rev.2.2) | `git\s+push\b.*(--force\b\|-f\b)` | ブロック |

実機 init 時に承認段階で発見・修正済み(机上テスト 8 ケースで検証)。テンプレート・設計書の例示はすべて新 regex に差し替える。教訓: **例示 regex は「すり抜けケース+誤発動ケースを含む机上テスト」とセットで提示する**(SKILL.md v0.2.1 の companion 生成規則に同要件を明文化済み)。

## 修正2: 脅威モデルへの追記(「失敗時挙動」節の脅威モデル)

rev.2.1 の整理:

> 守るのは「誠実なエージェントの逸脱・ミス・コンテキスト喪失」。Bash 経由のファイル書き換え等の迂回は悪意の領域であり、sandbox の守備範囲。

実機スモークテストでこの二分法の盲点が実証された。**Write ツールがファイル未読の内部制約で失敗した直後、エージェントは悪意なく、単なる代替手段として `echo >>` で保護パス(CONFIRM 対象)に書き込んだ。** つまり:

> **Bash 経由の書込は「悪意ある迂回」だけでなく「誠実なフォールバック迂回」としても発生する。** ツール失敗 → Bash で代替、はエージェントの自然な問題解決行動であり、まさに本エンジンが守るべき「誠実なエージェントのミス」の一形態である。

### 対応(v0.2.1 で実装)

層別合成で対応する。エンジン変更は不要(既存の command_regex 機構にルールを足すだけ)。

1. **固定 companion ルール `protect-harness-files-bash`**(最優先): ハーネス定義ファイルへの Bash 書込を deny。放置すると `sed -i 's/"deny": \[.*\]/"deny": []/' .claude/settings.json` が**実質的な権限昇格経路**になり、`echo garbage >> harness-rules.json` がフェイルクローズによる自己 DoS になるため、自己保護こそ最優先
2. **プロジェクト固有 path_glob ルールへの companion は提案制**: init がルールごとに確認。ask の companion はダイアログ発火点を増やすため、勝手に増やさない(ダイアログ疲れ対策と整合)
3. **rules.md 生成節に散文を組み込み**: 「編集ツールが失敗しても Bash を代替手段にしない。停止して人間に報告する」— プロンプト層でも塞ぐ
4. **本修正書(脅威モデル更新)**: regex の限界も明記する

### companion regex の設計

```
(>|\btee\b|\bsed\s+-[a-zA-Z]*i|\b(cp|mv|rm|truncate|touch|dd|ln)\b)[^|;&]*<パス断片>
```

- 構造: **書込動詞 + 同一パイプライン区切り内([^|;&]*)のパス断片**の共起。読み出し(`cat`/`grep`)、人間の修復手順(`git checkout`)、保護ファイルから他所への書き出し(`cat 保護 > /tmp/x`)では発火しない
- パス断片の規約: 固有名ファイル(harness-rules.json)は bare 名でも拾う(`cd .claude && echo >> harness-rules.json` 対策)。`settings.json` のような一般名は必ずディレクトリ接頭辞付き(他用途ファイルへの誤発動防止)
- 検証: 真陽性 12・偽陽性 8 の机上テスト ALL PASS+v0.2.0 エンジンでの E2E 確認済み(エンジン無変更で機能)

### 明記する限界

regex で拾えない経路: `cd` 後の短い相対パス(一般名の場合)、変数展開(`P=.claude/settings.json; echo x > $P`)、インタプリタ経由(`python3 -c "open(...,'w')"`)、エンコード・難読化。**ヒューリスティックの粗さは脅威モデルの粗さと釣り合っている** — 誠実なエージェントは素直なコマンドを使い、回避的な書き方をする敵は最初から L1+L2 の守備範囲外(sandbox の領域)。regex に拾えない誠実な迂回の根本解は **L3(意味判定)の守備範囲**として申し送る。

## 修正3: CONFIRM(ask)のモード別実効性(「CONFIRM のモード対応」節への実測追記)

rev.2 は「通常モード= ask(ダイアログ)/ bypass = deny+停止」の2分で記述していた。実機検証でモードは実質3つであり、実効性が異なることが判明:

| 実行モード | ask の挙動(実測) | 実効性 |
|---|---|---|
| 通常(default) | ダイアログは出るが、**全編集に出る標準確認と区別できない**(理由文も非表示 @ 2.1.175) | 低(標準確認に埋没) |
| **auto / acceptEdits** | **本来ダイアログが出ないモードで割り込み表示**(対照実験で確定: 非保護ファイルは無確認・保護パスのみ確認) | **高 — ask の主戦場** |
| bypassPermissions | deny+停止指示(専用文言)に変換 | 高(設計どおり) |

含意: Plan 承認 → auto 実行、という設計推奨フローの実行フェーズこそ ask が効く場面であり、設計意図(実行時バックストップ)と実測が噛み合っている。rules.md テンプレートにこの表を反映済み(v0.2.1)。

付随する実測: bypass 中の CONFIRM が専用文言で deny されたこと自体が、**stdin の許可モードキーの実在と detect_bypass() の機能の実証**である(スモークテスト #4 の差し戻し条件は不成立)。キーの正確な名前はフック stderr がデバッグログに記録されないため未取得 — detect_bypass 改修時に再確認する。
